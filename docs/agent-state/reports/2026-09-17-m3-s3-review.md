## 4. Findings

### BLOCKER
None.

### HIGH
- **H-1 — `isHidden()` semantics unverifiable from headers; loads both the REQ-SC-002a "shown" leg and the global drop-in for scratchpad windows.** `is_candidate()` gates every candidate path on `!w->isHidden()` (`hypr_window_source.cpp:26`) and is unchanged from M2, but the new adapter **adds** the claim that a *shown* special-workspace window is only excluded when `isHidden()` is false — the comment at `:22-24` asserts this is "redundant-but-consistent", which cannot be proven from the installed headers (`Window.hpp:318` is a declaration only, no `Window.cpp` shipped).
  - If `isHidden()` returns true for a windows on a shown special workspace, `is_candidate()` would drop the scratchpad before `scope_matches()` sees it → REQ-SC-002a "shown" leg **fails in every scope**, and the M2-global drop-in promise changes for scratchpads.
  - Mitigation: mandatory, written nest items 2-3 in plan §7 (scratchpad shown → candidate; hidden → absent). This review could not run the nest. **The §7 run must be green before merge**, and if the shown leg fails, the fix is scoping the M2 `isHidden()` gate in `is_candidate()` to `m_isMapped` only and letting the domain `hidden` flag own the special-workspace rule.

### MEDIUM
- **M-1 — `global` drop-in has one intentionally stricted delta: the live-refs tail now applies `is_candidate` where M2 pushed unconditionally.** M2: `for (ref : live_refs_newest_first()) fallback.push_back(ref);` (no gate). M3: `w && is_candidate(w) && scope_matches(...)` (`hypr_window_source.cpp:102-106`). For mapped windows the result is identical (the primary/history paths already gated); for unmapped/minimized/closed-but–pending entries the new gate is *stricter* and REQ-SNAP-002-correct. Not a regression for the test scenarios; flag for nest item 8 (M2 drop-in) only so the delta is observed/confirmed, not missed.
- **M-2 — `State::monitorState()->monitors()` "enabled-only" is an unconfirmed assumption** (plan §2 listed it; headers cannot decide `m_monitors` vs `m_realMonitors` semantics). If a disabled/mirror monitor is ever present in `monitors()`, its active(+special) workspace id enters `visible_workspaces` and the `hidden` leg, making a dormant workspace "visible". Not covered by a dedicated nest step (nest 4 uses 2 live monitors). Recommended: add a nest step with a disabled monitor, or document why `monitors()` is safe.

### LOW
- **L-1 (judgement call, Duplicated Code):** the candidate-filter idiom `is_candidate(w) && scope_matches(scope, derive_meta(w, focus), focus)` is repeated 3× (`hypr_window_source.cpp:98,104,111`). A small loop-local predicate (e.g. `fits(w)`) would DRY it and make a future filter change single-site. Not required — each site guards its own source differently.
- **L-2 (naming/cosmetic):** CHANGELOG labels the work "M3-S4 config surface complete" (`CHANGELOG.md`) while issue #20 is M3-S3 with S3-4 as an acceptance criterion; PROGRESS M3-S3 title still says `debug_scope` (no such key exists in SPEC §4). Doc residue only.
- **L-3 (note):** S3-4 wording "fall back to default + once-warn on invalid" — the once-warn is implemented for `ui=border/external` (unimplemented backends), **not** for invalid enum strings (REQ-CFG-001 = "MAY notify", so no-warn is compliant). Pre-existing M2 behavior; not a regression.
- **L-4 (note):** `visible_workspaces.push_back(active)` in `current_focus()` is not null-guarded for `WORKSPACE_INVALID` (a monitor edge case at startup would push `0xFFFFFFFFFFFFFFFF`). Benign: it never matches a real workspace id; the special id is guarded already (`:48`). Not worth code change.
