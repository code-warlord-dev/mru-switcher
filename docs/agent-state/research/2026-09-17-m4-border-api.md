# M4-R0 — Border highlight API on Hyprland 0.56.2 (efb5099)

Pin: `efb50993780079460b0cbed1363e2166a2de1d9f` (= v0.56.2). All upstream claims cited to blob/raw links at this commit, `main` is never cited. All Hyprland paths below are `src/<path>` in the repo root.

## Problem

M4 (`ROADMAP.md` M4, ~lines 120–137) needs a `BorderHighlightUI`: a visible per-window border highlight on the **currently selected** window while a session is Active, updated on every `mru:cycle`, cleared on apply/cancel, with zero focus side effects (REQ-F-003) and none of the visual artifacts of real focus. `UIPort` gives us `on_session_start(snapshot, index)` / `on_selection_changed(index)` / `on_session_end(UIEndReason)` (`include/mru/domain/ui_port.hpp:13-20`); the domain must never learn which mechanism is used (ADR-007). The question is **which compositor mechanism to use and how to guarantee restore**.

Sources used: extracted source of the pin (`/tmp/opencode/hypr-src/Hyprland-efb5099…/`) + `hyprwm/hyprland-plugins` borders-plus-plus (pattern check). No live nest run in this memo (M4-S3 proposal below).

## Recommendation

**Option A: per-window `inactive_border_color` + `active_border_color` via `invokeHyprctlCommand` on the compositor main thread.**

- Only public/stable surface: `HyprlandAPI::invokeHyprctlCommand` (PluginAPI.hpp:191) driving core dispatcher `setprop` and hyprctl `getprop`. Nothing in the plugin's .so touches internal Hyprland types, so this does **not** require the private-ABI carve-out that decoration `draw()` needs.
- Set **both** slots to the highlight color; the selected window is normally the *non-focused* one, so `inactive_border_color` is the governing slot (F4), but if `len==1` `start_offset=second` selects the focused window, `active_border_color` keeps it highlighted; overrides are priority-protected from rules/groups (F5) and follow the window on mid-session focus shifts (F15).
- No focus side effect: neither `setprop` nor `getprop` touches `focusState()`; REQ-F-003 holds.
- REQ-UI-001/002 mapping: wrap every call, treat `unknown request` / `Invalid prop name` / empty result as "backend unavailable" → `null` fallback + warn-once (`mru_plugin.cpp:216` currently hardcodes `NullUI`; M4 swaps it for the config-driven pick, `config_value.cpp:54-62` already parses `Border`).
- 4 getprop/setprop round-trips per selection change, each ending in an O(mapped-windows) recalc (F6) — acceptable for selection-only traffic, but the SchedulerPort/`mru:cycle` hot path stays well under any per-frame budget; confirm in nest.

Choose **B** only if the nest shows A's recalc latency is user-visible (unlikely) or if "no true unset" (F10) is judged non-negotiable at M4.

## Restore strategy

- **Capture-effective, restore-by-value.** On first highlight of a window, read `active_border_color` and `inactive_border_color` via `getprop` (`valueOr`, i.e. the true effective color F8) and store `{WindowRef, active, inactive}` for the session. On selection change / session end, write the captured values back through the **same** `setprop` path.
- **Do not use `-1` as "restore".** At this pin `-1` produces an empty gradient which the renderer draws as **no border** (F10) — that removes the border instead of restoring the user's color. (Nest-verify: whether a 0-length border shader pass degrades to the global fallback — if it does, `-1` becomes an acceptable restore; current source reading says invisible.)
- **Unload.** `PLUGIN_EXIT` (via `teardown_state()` in `mru_plugin.cpp`) MUST call `on_session_end`/restore on every snapshot window before the UI backend is destroyed. Known gap: an abrupt kill/eject while Active leaves overrides stuck until Hyprland restart (no auto-unset, F10/F12). Accepted for M4 (same class of risk as any window-prop tooling); document in USER.md.
- **No "stuck" cross-contamination on reload.** `config.reloaded` re-evaluates rules at `PRIORITY_WINDOW_RULE` < our `PRIORITY_SET_PROP` (F5), so mid-session reloads cannot erase or clobber the highlight; `ui`-backend change takes effect next session (REQ-CFG-003).

## Minimal config surface

Per SPEC §4 conventions (keys under `plugin:mru-switcher:`, registered only in `PLUGIN_INIT`; reserved keys registered+documented — ADR-016 __5__ precedent):

| Key | Type | Default | Notes |
|-----|------|---------|-------|
| `ui` | string | `null` | Existing (SPEC §4). `border` selects the backend in M4; REQ-UI-003 still lets default switch to `border` in a minor release with CHANGELOG note. |
| `border_color` | string (gradient) | fixed accent (e.g. `0xffffd9a0`) | **New (recommended).** The highlight color. A single string keeps the `getprop` value-format symmetric ("`rrgbbbaa` [..] `deg`"). Default is a user-output-visible behavior, so register it — do not hardcode silently. |
| `border_width` | — | — | **Defer.** `setprop border_size` triggers layout recalc (option D); ROADMAP M4 says "border colour / opacity", not width. Adding the key later is additive (pre-1.0) and does not need an ADR of its own if SPEC is updated in the same change set. |

`ui` alone is *technically* sufficient (hardcode a highlight color) but violates the repo's "every documented behavior has a config row" convention (SPEC §4, ADR-016 __5__); `border_color` is cheap and warranted. `border_width` is NOT warranted at M4.

## SPEC / ADR impact

- **REQ-UI-001** (UI failure must not abort apply/cancel): implement by try/catch + result-string checking around every `invokeHyprctlCommand`; the UI layer never throws into `SessionController`. Needs a test row or an explicit nest + a T-UI-* extension.
- **REQ-UI-002** (unimplemented/unusable backend → null + warn-once): BorderHighlightUI must probe usability at construction (e.g. a getprop probe); any failure degrades to `NullUI` with a single `addNotification`. T-UI-01 already covers the parse-level fallback; extend for runtime probing.
- **REQ-UI-003**: default stays `null` at M4 (safer; ADR-011 already permits a later flip with CHANGELOG) — decision for ADR-017, not code.
- **ADR-017: YES, it must exist.** It must decide, before/with code:
  1. `setprop active/inactive_border_color` via `invokeHyprctlCommand` is the M4 mechanism (public, low-ABI), with decoration (B) as documented fallback — not both in v0.x.
  2. `border_color` key: name, type (gradient string), default, and that `border_width` is explicitly deferred.
  3. Restore-by-value ("capture effective color, re-set at end") and the accepted stuck-on-abrupt-termination gap; no `-1` reset without a nest-shown fallback.
  4. Default remains `ui=null` at M4; keep `null` default config; `border` explicit opt-in.
  5. Restore must run in `teardown_state()` before UI destroy; extend `docs/COMPAT.md` matrix with this mechanism.
  Also update SPEC §4 table (add `border_color`) and traceability (`docs/REQ-TRACE.md`) in the same change set.

## Open questions / proposed live nest experiment

Top open question changing the design: **does `setprop … <color>-1` (empty gradient) render as *invisible border* or silently fall back to the global border color?** If it falls back, restore can use `-1`; if invisible, restore-by-value is mandatory (current reading; F10).

M4-S3 nest steps (recipe from `docs/COMPAT.md` line ~47; host pid 1245 is **off-limits**):

1. Start nest (aquamarine 0.15.0, Wayland backend per COMPAT); open 3 terminals; load the M4 plugin with `ui=border`, `border_color` default.
2. Wire bind `ALT,TAB → mru:cycle next`, `bindrt ALT → mru:apply`, `bind ALT,ESC → mru:cancel`.
3. **Capture probe:** from `hyprctl dispatch setprop` on the *host-independent* nest SIG, verify `setprop address:0x<ptr> inactive_border_color 0xffff0000` + `active_border_color …` visibly recolor the window, and are not clobbered by `config.reloaded` (F5/F6).
4. **Restore probe:** record `getprop` output before/after; set each slot to `-1` and observe: border invisible or user-color? Decides the restore strategy.
5. **Session checks:** cycle×3 → only selection window borders highlight, `hyprctl activewindow -j` unchanged (REQ-F-003); mid-session FFM to another window → highlight stays (F15); apply → exactly one focus + all borders restored (M4 exit "no stuck borders"); cancel with `restore_focus_on_cancel` → restore too.
6. **Tab-while-focus-toggles:** select the focused window (len==1) → active slot path exercised.
7. **Unload:** `plugin unload` mid-session → no crash, borders restored (REQ-H-008 + F12 note); then `plugin unload` **graceful-on-idle** and confirm no leftover overrides via `getprop` (should equal global default `valueOr`).
8. **Perf smoke:** cycle 100× in a loop; assert no perceptible stutter (F6 O(n) recalc budget).
9. **Failure path:** temporarily point at a bogus prop name in a test build → expect warn-once + `null` behavior, apply/cancel unaffected (REQ-UI-001/002).

Pass = M4 exit criteria from ROADMAP: daily-driver usable with `ui=border`; no focus flicker; no stuck borders after cancel.
