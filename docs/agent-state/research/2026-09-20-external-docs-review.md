# Ревью и рекомендации: Hyprland MRU Windows Switcher

**Дата:** 2026-09-20  
**Статус:** Живой документ (ревью документации + архитектура доставки, конфигурации, безопасности и восстановления)  
**Цель:** Собрать все выявленные проблемы и предложения в одном месте. Дать автору готовые prompt-спеки и конкретные направления улучшений.

---

## Общий контекст

Техническая реализация плагина оценивается как очень сильная (fail-closed hash check, чистые контракты, hexagonal-подход, аккуратная работа с identity/generation). Основные точки роста лежат в:

- Подаче информации (документация)
- Опыте установки и обновления
- Удобстве и безопасности конфигурации
- Обработке ошибок и восстановлении состояния
- Защите нового surface (external overlay)

Все предложения ниже направлены на снижение когнитивной нагрузки, повышение actionable-ценности и укрепление отказоустойчивости. Ломать существующую архитектуру не требуется.

# Часть 1. Документация

## 1.1. Размытие границ между пользовательским и разработческим контекстом

### Проблема

Пользовательские файлы (`README.md`, `USER.md`, `API.md` и аналогичные) сильно загрязнены внутренними идентификаторами и инженерным сленгом:

- `REQ-001`, `REQ-UI-008`, `REQ-UEI-002` и т.д.
- Ссылки на `ADR-018`, `ADR-020` и другие архитектурные решения
- Технические названия вроде `M5 External Overlay Protocol`

Это классическое проявление закона Конвея в документации: внутренняя структура разработки «просачивается» во внешний интерфейс. Даже технически грамотная аудитория Hyprland не обладает бесконечной когнитивной пропускной способностью.

### Рекомендация

Установить жёсткую терминологическую и структурную границу:

- Пользовательские инструкции → только конечный результат, юзкейсы, синтаксис, готовые примеры.
- Вся трассировка требований, номера спецификаций, ADR и глубокая внутренняя механика → только в developer/contributor-разделы.

### Prompt-спека

```text
Задача: Жёстко разделить пользовательский и разработческий контекст в документации плагина Hyprland MRU Windows Switcher.

Контекст проблемы:
Пользовательские файлы (README.md, USER.md, API.md и аналогичные) содержат внутренние идентификаторы требований (REQ-*, REQ-UI-*, REQ-UEI-*), ссылки на ADR и технический сленг (например, «M5 External Overlay Protocol»). Это создаёт избыточную когнитивную нагрузку даже для технически грамотных пользователей.

Требования к результату:

1. Из всех пользовательских файлов полностью удалить:
   - Идентификаторы вида REQ-*, REQ-UI-*, REQ-UEI-* и любые другие внутренние номера требований
   - Прямые ссылки на ADR (ADR-018, ADR-020 и т.д.)
   - Технические кодовые названия механизмов, которые не несут ценности для конечного пользователя

2. Заменить технический сленг на описание конечной пользы. Пример:
   Было: «M5 External Overlay Protocol»
   Стало: «Включает поддержку пользовательских виджетов и интерфейсов» (или более точная формулировка по смыслу)

3. Всю удалённую информацию по трассировке требований и архитектурным решениям перенести в один из вариантов:
   - Отдельный файл DEVELOPER_API.md / CONTRIBUTING.md / DEVELOPER.md
   - Или оставить только внутри SPEC.md / архитектурных документов

4. Пользовательские разделы конфигурации должны содержать:
   - Чистое описание опций с точки зрения результата
   - Готовые рабочие примеры конфигурации без аббревиатур
   - Визуальное или структурное отделение базовых настроек от экспериментальных

5. Сохранить всю техническую точность. Ничего не упрощать до потери смысла — просто правильно позиционировать информацию.

Критерий готовности:
Пользователь, открывший README / USER / API, должен иметь возможность настроить плагин, не спотыкаясь о внутренние идентификаторы и не уходя в ADR.
```

## 1.2. Концептуальная фрагментация материалов по безопасности и отказам

### Проблема

Информация о защите и поведении при сбоях разбросана по `SECURITY.md`, `FAILURE_MODES.md` и спецификациям. Читателю (особенно аудитору) приходится самостоятельно собирать полный сценарий из нескольких файлов. Это создаёт высокую когнитивную нагрузку и риск упустить целостную картину.

### Рекомендация

Перейти от изолированных матриц к **повествовательным профилям рисков** (Risk Life Cycles). Каждый профиль прослеживает угрозу от возникновения до разрешения/деградации и привязан к интеграционным тестам.

### Prompt-спека

```text
Задача: Устранить концептуальную фрагментацию документации по безопасности и отказам плагина Hyprland MRU Windows Switcher путём создания повествовательных профилей рисков (Risk Life Cycles).

Контекст проблемы:
Информация о защите и поведении при сбоях разбросана по SECURITY.md, FAILURE_MODES.md и спецификациям. Читателю приходится самостоятельно собирать полный сценарий из нескольких файлов.

Требования к результату:

1. Создать раздел (или отдельный документ) с повествовательными профилями рисков. Каждый профиль — связный рассказ:
   - Как возникает угроза / сбой
   - Какие защитные механизмы срабатывают
   - Как происходит деградация или восстановление
   - Какой конечный безопасный результат получает пользователь

2. Обязательные примеры профилей:

   a) «Сбой внешнего оверлея»
      - Ограничение сокета AF_UNIX (64 КБ)
      - Режим отказа FM-008
      - Переход на Null UI
      - Ссылки на интеграционные тесты

   b) «Вредоносная / некорректная конфигурация»
      - Обработка значений, скопированных из интернета
      - Безопасный откат к дефолтам
      - Отсутствие опасного парсинга

   c) «Шторм закрытия окон»
      - Поведение при массовом закрытии окон во время переключения
      - Обрезка снимка сессии
      - Гарантии отсутствия обращения к освобождённой памяти

3. Каждый профиль должен содержать прямые ссылки на интеграционные тесты (гарант актуальности).

4. Существующие матрицы сохранить как reference, но основным способом потребления сделать повествовательные сценарии.

Критерий готовности:
Аудитор или разработчик может прочитать один профиль целиком и полностью понять защиту и деградацию без прыжков по файлам.
```

## 1.3. Отсутствие пользовательского пути восстановления при несовместимости версий

### Проблема

Плагин использует правильный fail-closed механизм проверки хеша заголовков. Однако после обновления Hyprland пользователь получает непонятную ошибку и нерабочий плагин. В `COMPAT.md` это описано только как инженерное ограничение.

### Рекомендация

Превратить раздел совместимости в практическое руководство по восстановлению: реальные фрагменты логов, готовые команды, actionable-уведомления.

### Prompt-спека

```text
Задача: Переработать раздел совместимости (COMPAT.md и связанные места) из инженерной констатации ограничений в практическое руководство по восстановлению для конечного пользователя.

Контекст проблемы:
Плагин использует fail-closed проверку хеша заголовков. Это защищает от segfault, но после обновления Hyprland пользователь остаётся без понятного пути восстановления.

Требования к результату:

1. Сохранить всю техническую строгость проверки совместимости.

2. Добавить чёткий блок восстановления:
   - Реальный фрагмент лога с ошибкой несовпадения хеша + пояснение «Это штатное срабатывание защиты».
   - Готовые команды: hyprpm update + шаги пересборки через CMake.
   - Краткая инструкция «что делать прямо сейчас».

3. Рассмотреть helper-поведение: при падении из-за хеша выводить через notify-send actionable-текст («Выполните hyprpm update…»).

4. Не дублировать общую документацию экосистемы Hyprland. Брать ответственность только за ошибку этого плагина.

Критерий готовности:
После обновления Hyprland пользователь за 30–60 секунд понимает, что произошло, и самостоятельно возвращает плагин в рабочее состояние.
```

# Часть 2. Доставка и установка (Installer)

## 2.1. Текущее состояние

- Основной путь — `hyprpm` (есть `hyprpm.toml`).
- Ручная сборка через CMake.
- Жёсткий pin на конкретный коммит Hyprland (0.56.2).
- `commit_pins` в `hyprpm.toml` пока пустые.

## 2.2. Что такое commit_pins и коммит плагина

**commit_pins** — механизм версионирования плагинов в `hyprpm`.

Hyprland не имеет стабильного ABI. Поэтому `hyprpm` при установке смотрит текущий коммит композитора и ищет в манифесте плагина подходящую пару:

```toml
commit_pins = [
    ["хеш_коммита_Hyprland", "хеш_коммита_плагина"],
    ...
]
```

- Первый хеш — коммит Hyprland.
- Второй хеш — **коммит плагина** (обычный git-коммит в репозитории mru-switcher), который был проверен и признан совместимым с этим коммитом Hyprland.

Если точного совпадения нет — hyprpm берёт latest или отказывается собирать. Без нормально заполненных `commit_pins` пользователи на разных версиях Hyprland будут получать либо ошибки сборки, либо потенциально несовместимые бинарники.

## 2.3. Варианты доставки и рекомендации

| Вариант | Плюсы | Минусы | Рекомендация |
|---------|-------|--------|--------------|
| **hyprpm (основной)** | Официальный, автоматически подтягивает headers | Требует сборки у пользователя, зависит от качества commit_pins | Основной путь. Срочно заполнить commit_pins |
| **Prebuilt .so + install-скрипт** | Быстрый старт | Нужно собирать под разные версии, риск ABI-mismatch | Только как дополнение + жёсткая проверка хеша |
| **AUR / distro packages** | Нативная интеграция | Долго поддерживать | Низкий приоритет |
| **Nix flake** | Идеальная воспроизводимость | Меньшая аудитория | Желательно иметь (особенно под Omarchy) |
| **Однострочный bootstrap** | Низкий барьер входа | Безопасность (curl\|bash) | Thin wrapper над `hyprpm add` |

### Конкретные улучшения

1. Заполнить и поддерживать `commit_pins` для всех поддерживаемых релизов/коммитов Hyprland.
2. В `PLUGIN_INIT` при несовпадении хеша — понятное notification + текст «Выполните `hyprpm update`».
3. Добавить простой `install.sh` рядом с репозиторием (проверка зависимостей + предложение hyprpm или ручной сборки + готовый блок конфига).
4. В GitHub Releases класть `.so` + sha256 + точный COMPAT-хеш Hyprland, под который собрано.
5. Долгосрочно — поддержка нескольких major-версий Hyprland через conditional compilation / feature-flags (дорого).

# Часть 3. Конфигурация

## 3.1. Текущее состояние

Идиоматичный блок `plugin { mru-switcher { ... } }`. Это правильно.

## 3.2. Направления улучшения

**A. Диагностика и DX**
- Расширить `mru:status`: текущие настройки, состояние сессии, активный UI backend, последняя ошибка, версия + хеш сборки.
- При `config.reloaded` — мягкая валидация с warn-once notification при выходе значений за допустимые пределы.

**B. Профили / пресеты**
```conf
plugin {
    mru-switcher {
        profile = niri-like   # windows-like | minimal | power-user
        # ... точечные оверрайды
    }
}
```
Пресеты живут внутри плагина. Снижает барьер входа.

**C. Разделение базовых и продвинутых ключей**
В документации (и по возможности в runtime) явно отделять core-опции от advanced.

**D. Валидация и миграции**
- Жёсткий clamp + понятное сообщение вместо silent fail.
- При появлении deprecated-ключей — warn + автоматическая миграция, если возможно.

**Рекомендация:** не изобретать свой формат конфига поверх hyprlang. Оставить текущий подход, добавить профили и сильно улучшить диагностику.

# Часть 4. Безопасность

## 4.1. Уже хорошо

- Fail-closed по хешу заголовков.
- Лимит размера сообщения на AF_UNIX (64 КБ) для external overlay.
- Работа в адресном пространстве композитора (любая ошибка критична — это осознанно).

## 4.2. Что усилить

### External Overlay (самый опасный новый surface)

- Socket только в `XDG_RUNTIME_DIR` с правами `0600`.
- Обязательная аутентификация (shared secret / token, который плагин генерирует).
- Rate-limiting + максимальный размер одного JSON-сообщения.
- Жёсткий whitelist разрешённых команд от overlay.
- При любой аномалии — немедленный drop соединения + fallback на Null/Border UI + notification.

### Конфигурация

- Все строковые значения (цвета, пути) — жёсткая валидация и sanitize.
- Никакого eval-подобного поведения.

### Память и ресурсы

- Лимит размера snapshot + политика вытеснения.
- При «шторме» закрытия окон — быстрый и безопасный invalidate всех WindowRef с проверкой generation.

### Supply-chain

- Продолжать подписывать релизы (GPG уже есть).
- В документации явно предупреждать: не загружайте `.so` из неизвестных источников.

# Часть 5. Обработка ошибок и восстановление состояния

## 5.1. Принципы

- **Fail-closed** — там, где ошибка может уронить композитор.
- **Fail-soft / graceful degradation** — везде, где можно продолжить работу (особенно UI).
- **Observability first** — любая деградация должна быть видимой (notification + лог + `mru:status`).

## 5.2. Желаемое поведение по сценариям

| Сценарий | Желаемое поведение |
|----------|---------------------|
| Несовпадение хеша Hyprland | Плагин не грузится + понятное notification + инструкция `hyprpm update` |
| Ошибка external overlay | Немедленный fallback на Null/Border UI + notification |
| Битый/невалидный конфиг | Warn-once + безопасные дефолты |
| Window умер во время сессии | Selection сдвигается или сессия отменяется (через generation) |
| «Шторм» закрытия окон | Snapshot аккуратно инвалидируется, без обращения к freed memory |
| Выгрузка/перезагрузка плагина посреди сессии | Корректный cleanup, без утечек и dangling focus |

## 5.3. Восстановление состояния

- **Сессия** — эфемерна. При серьёзном сбое просто умирает (cancel).
- **MRU-история** — можно сделать более живучей (опциональная персистентность — низкий приоритет).
- **UI**:
  - Border UI обязан «отпускать» все border'ы при любом выходе из сессии.
  - При разрыве сокета external overlay сессия считается отменённой.
- **Диагностика** — `mru:status` должен отдавать:
  - Состояние сессии (Idle / Active)
  - Текущий scope и размер snapshot
  - Активный UI backend + health
  - Последнюю ошибку
  - Версию плагина + хеш, под который собран

# Сводка приоритетов

| Приоритет | Что делать | Зачем |
|-----------|------------|-------|
| **Критический** | Понятные сообщения + recovery-path при hash mismatch | Самый частый и болезненный UX-провал после обновлений |
| **Критический** | Жёстко закрыть безопасность external overlay | Новый attack surface |

| **Средний** | Профили конфигурации | Снижение барьера входа |

## Рекомендуемый порядок действий

1. Закрыть recovery-path при несовместимости версий + улучшить сообщения.
2. Укрепить безопасность external overlay.
3. Заполнить `commit_pins` и довести hyprpm-опыт.
4. Расширить `mru:status`.
5. Почистить пользовательскую документацию (часть 1).
6. Добавить профили конфигурации и повествовательные профили рисков.

После внесения изменений имеет смысл вернуть обновлённые файлы на повторный разбор.
